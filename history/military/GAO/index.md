# Georgian Army Officers

The [Georgian Army Officers database](https://www.georgianarmyofficers.org/) (GAO) makes a slice of history from The National Archive available to researchers and the wider public.
It's part of a wider effort that aims (among other things) to support citizen science, so here goes ...

## An overview

The [National Army Museum](https://www.nam.ac.uk/) are a partner in the GAO project.
They publicised the finished database to museums in their [Regimental Corps and Museum networks](https://www.nam.ac.uk/regimental-and-corps-museum-networks),
including the [Royal Hampshire Regiment Museum](https://www.royalhampshireregiment.org/), where I volunteer, and the curator asked me to take a look.
I wrote [a brief review](https://tigersmuseum.github.io/history/docs/gao) for the museum's GitHub pages.
That has an overview of the project and how it might be used, and I'll update it with any useful historical information I come up with.

I want to identify individual officers, collect their entries across army lists that mention them, and build a _service history_ for each.

## Entity Linking

The source data for GAO is [Army Lists](https://en.wikipedia.org/wiki/Army_List).
An officer's service record appears across multiple lists, so collecting records to form a service history is an 'entity linking' problem.
The GAO database uses as statistical method to do this, but I've developed any alternative method that I want to try.

I start by extracting all GAO records for a single unit, the 67th Regiment of Foot.
Next, I extract all the names from these records and make list.
This [list of names](https://github.com/knoxa/linked-text/blob/master/projects/gao/input/names-67.txt) is the starting point for [my entity linking method](https://github.com/knoxa/linked-text/tree/master/projects/gao).
The [result](https://github.com/knoxa/linked-text/blob/master/projects/gao/results/latest-67.xml) is sets of names that represent the same officer.

## Service history

I now have sets of names that each represent the same officer.
I build a service history for each officer as follows:

1. For each set, I collect the GAO records that mention any of the names.
This gives me sets of records that, I hope, each represent an officer.

1. I sort the records in each set in ascending time order (`fileyear` field).
At this point, I have the same data structure generated by the GAO entity linking method and that might be produced by any other method.

1. I parse each set looking for records that have both `reg_rank` and `reg_date` set.
These give a record of promotions that I can pull out to make [service histories](results.xhtml).
These results are XHTML, so that they are both human and [machine readable](format.md).

1. I assess the sets of GAO records critically in various ways, and raise comments, questions and objections as _claims_ that I append to the service history.
I add these to the XHTML.

1. I look at the results and the claims, and decide whether they're plausible.
Some inconsistencies are due to transcription errors, and I may have to go back to the source data to resolve these.
I can make any corrections to the entity linking output that are suggested by this analysis, then go back to step 1 above.

### Issues

1. I've made things easier for myself by selecting data for a single regiment (67th Foot), but officers may move between regiments, so I can't claim I've created complete service records.

1. Some of the GAO records just have a surname and there are different people with the same surname in the regiment.
These records, as things stand, are genuinely ambiguous.
I end up with multiple copies of these records in my output.
The GAO database linking method checks that records for an officer look sensible when ordered in time. Rank should increase for example.
I'll need to do something similar to resolve ambiguities.

1. Some officers have long careers in the regiment that cover large parts of the 1790-1820 timeframe, so produce lots of records.
Others produce few records.
Where few records appear, it might because the officer's career just clips the 1790-1820 window, or it might be that they join as an Ensign and soon move on promotion to another regiment, or they might come in at one promotion and move out on the next.
I will need to take moves between regiments into account if I want to build complete service histories.
Sometimes there's information in the `annotations` field that can help find these moves.

I can derive sets of records that I believe belong to the same officer, but I can't be sure of that.
It's likely that those sets of records don't represent the full service history of the officer.

### Corroboration

I can look for War Office notices in The Gazette.
I've selectively transcribed bits of them, and I'd like to make this data re-usable, so I'm capturing [Gazette transcripts](gazette.xhtml) as XHTML with semantic mark-up.

One problem with searching the Gazette is that it's text index relies on OCR which is not always reliable.
The name you're searching for might appear in an issue of the Gazette but not be identified by the system.

## Identification

I have sets of records that refer to individual officers. I need to _identify_ each set with a specific person.

I can address ambiguity in entity linked sets as described above, and I can check the sequence of records makes sense as all or part of a service history. 
At the end of this process, I can assume that each set of linked records really does represent a person.
The collected information in the set is a form of identity.
I may be able to condense the information in the set to produce an equivalent set of attributes that represent an individual, names and a list of promotions and appointments for example.

I'd like to go a step further and associate each set of records with a persistent _identifier_ that represent the officer.

## Identifiers

The GAO database defines explicit identifiers for officers.
I can assign one of these identifiers to each set, but the problem is that my entity linking results do not necessarily match those in the GAO database.
I might not find a matching GAO identifer, and I might find more than one matching identifier.

DBpedia has [categories for British  Army officers](https://en.wikipedia.org/wiki/Category:British_Army_officers).
These can be used in SPARQL queries to find officers in a particular regiment. For example, this query:

I want to reuse identifiers rather than invent them.
I might assign identifiers to sets of records in order to more easily manage them, but these won't be persistent.
I'll try and replace these with properly curated identifiers when I can find them.
Failing that, I'll aim to collect a consolidated set of information that describes a unique individual.
There will still be a identification step need at some future point, but I can make this identification as easy as possible by collecting together as much information as possible.

## Dialogue

Different entity linking methods will have different strengths and weakness.
My method divides names into sets of tokens, then works on the similarity between those sets.
The GAO method compares names with an 'edit distance' similarity metric that will catch cases that I might miss.
For example, GAO matches "R B Harrison" and "R B H arrision", but I don't make this match because I get 3 tokens in one case and 4 in the other, and they only overlap with the "R" and "B".

I see my entity linking method as making claims that need [checking](checking.md).
Each claim is a set of GAO records that are asserted as belonging to the same officer.
I can construct a 'GAO claim' by selecting records from the row data that have the same value in the `person` field, but it seems that some of GAO work on entity linking postdates the dataset.
There is a download option from a person record in the web application that would give the latest results, but download format is PDF.
The information is there, but needs parsing. The option for a (more) machine readable format would be nice.

A service history is a sequence of records.
There will be a first and last record in the sequence.

There are some questions that can be asked about a service history:

* _Do we have the first record?_
Presumably each service record should start with a commision as Ensign.

* _Do we have the last record?_
Sometimes there are handwritten annotations in the army lists that say an officer has resigned or died. This sort of information may also be available from other sources.

* _Is the service history continuous?_
If there are gaps, can we account for those gaps?

These researchers are helped by the GAO database, but could also help it, by confirming or correcting results.  

The question is how to go about it.
The pieces need to fit together.
One way to do this is to assign identity, to make it easier to relate pieces for the same officer.
It would also be nice to know where the boundaries of any peice of research lie.
For example, in researching for members of the 67th Foot, I will come across a record of an officer moving to or from another regiment.
This is the beginning or end of thread I'm interested in, but there's a connection to any research someone else might do into the other regiment.

I should try and make this useful.
I can produce lists of officers and the alternate regiments in which they served. A standard way of doing this?
In aggregation, the network of connections between regiments would be interesting to develop.
